# FireWeave — environment configuration

This repo is wired to the FireWeave project **arcade** (`a329f393-cab4-4853-953e-7ef70dc45ae5`).
Local development needs nothing configured. **Every deployed environment needs
two variables per surface**, and this file is the list.

Scaffolded 2026-10-06 by `/fireweave:initialise`. It contains no secrets —
only variable names and a link. Commit it.

---

## 1 · Issue the keys

Both keys are issued in the portal, and only there:

**[Project settings → API keys](https://app.fireweave.ai/projects/a329f393-cab4-4853-953e-7ef70dc45ae5/settings?tab=api-keys)**

That page has two panels, and they are not interchangeable:

| Panel | Key | Where it may go |
| --- | --- | --- |
| **Project API keys** | `project-api-key_…` | Server-side only — never a browser bundle, never a commit |
| **Browser keys** | `fw_public_…` | Designed to ship in a web bundle; scoped to `flags:evaluate` + `events:write` |

Each raw key is shown **once, at issue time**. FireWeave stores only its
SHA-256 hash and cannot show it to you again — if you lose one, revoke it in
the same panel and issue another.

Issue one key per deployed environment rather than sharing one across staging
and production. Both panels list what is active and let you revoke
individually, which is only useful if the keys are distinguishable.

## 2 · Set the variables

| Surface | Variable | Value |
| --- | --- | --- |
| **Server** (ts-server · python · java · swift) | `FW_API_URL` | `https://app-server.fireweave.ai` |
| | `FW_PROJECT_API_KEY` | from **Project API keys** |
| **Web** (browser bundle) | `PUBLIC_FW_API_URL` | `https://app-server.fireweave.ai` |
| | `PUBLIC_FW_PROJECT_API_KEY` | from **Browser keys** |

> **Vite projects:** Vite only exposes variables prefixed `VITE_`. Use
> `VITE_FW_API_URL` and `VITE_FW_PROJECT_API_KEY`; the harness reads either
> prefix. Every other bundler uses `PUBLIC_`.

Set them wherever this repo's deployments already get their environment —
GitHub Actions repository secrets, your VM's process environment, the
`environment:` block of a compose service, your platform's dashboard.
FireWeave does not need to know which; nothing here reads a FireWeave-specific
secret store.

**Do not put either key in `.env`, `.env.local`, or any committed file.** The
browser key is safe to *serve* to a browser — that is what it is for — but a
committed key is a key you cannot rotate without a commit.

## Local development needs none of this

The dev tier runs FireWeave's local provider: flags evaluate in-memory and
nothing leaves the machine. If neither variable is set, that is the path you
get, and it is the intended one.

The switch is the environment NAME your app reports, not the presence of a
credential — see `fw-providers` in each harness for how this repo resolves it.

## If a variable is missing in a deployed environment

**The harness refuses to boot, loudly, naming the variable.** That is
deliberate, and worth understanding before you try to "fix" it.

The alternative — falling back to local evaluation when a credential is absent —
produces a green boot, a healthy log line, and every control point silently
serving its default value. The observable symptom is a feature that never ramps,
which is indistinguishable from a rollout nobody started. A missing credential
is a deployment error, so it fails like one.

## `FW_ATTEST_URL` (legacy)

Older scaffolding wrote the fw-server base URL as `FW_ATTEST_URL` /
`PUBLIC_FW_ATTEST_URL`. The name is vestigial — it predates this path and
nothing about it attests anything. The harness still reads it when
`FW_API_URL` is absent, and warns once at boot when it does.

If you see that warning: rename the variable in your deploy environment. The
value does not change.

## Rotating a key

Issue the new key first, set it in the deployed environment, confirm the app is
serving traffic, then revoke the old one in the same panel. Revoking first takes
the environment down for as long as rolling out the new value takes.
